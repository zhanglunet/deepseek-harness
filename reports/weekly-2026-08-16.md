## 二、内容亮点

分析里有三块是从源码挖出来、其他公开分析没有覆盖的：

**1. 包依赖结构（现算，非转述）**
遍历 219 个 `package.json` 统计扇入：`session` 84、`llm` 82、`agent` 61、`tools` 47 构成核心骨架；`invariants` 被 218/219 个包依赖，是全仓库唯一的普遍依赖。

**2. 可重建性：日志即真相**
dsh 保证"凡是进入模型请求的内容都能从会话日志重建"，而这**不是文档承诺，是每次请求都实际执行的断言**——`agent-loop` 的不变量伴生包在每个 `llm/stream` 上比对 `JSON.stringify(实际 messages) === JSON.stringify(deriveMessages())`，逐字节相同才放行。这条在合规、审计、事故复盘场景下是硬通货，目前没看到其他分析写过。

**3. 生态地图**
按 star 抓取头部仓库归类，得出"UI 方向最卷、工程向工具集稀疏"的判断，并指出官方**不接受外部 PR**（`CONTRIBUTING.md` 明确写明）——这解释了公开仓库 PR 数为 0 而提交数上万的反常现象：开发在私有仓库，公开仓库是发布镜像。

**4. 回放 Demo 用的是真实数据**
本地无 API key，因此没有编造 transcript，而是使用仓库中已提交的快照 golden（`test:snapshot` 平时就是无密钥回放它们）。左侧渲染对话、右侧同步显示对应的日志原文——把第 2 点的论断变成可以自己点着看的东西。

## 四、需要决策的问题 ⚠️

### 插件目录只能覆盖 25%

GitHub 搜索接口**最多返回 1000 条结果**，与总数无关。生态涨到 4,022 个之后：

```
已列出   999 / 4,022   （25%）
未列出   3,023
```

页面已如实标注这一限制，但覆盖率会随生态增长继续下降。

**建议方案**：把单次查询按 star 区间切片（如 `stars:>100`、`stars:50..100`、`stars:10..49`…），每片各自不超过 1000 条，分片抓取后合并。代价是每日 API 调用量上升，需评估配额。

**需要你拍板**：是投入做分片抓取，还是接受"只收录头部 1000 个"并把页面文案改得更明确（例如直接叫"热门插件目录"）。我倾向前者——但如果生态继续这个涨法，分片规则也需要定期维护。

## 五、工程复盘：五个 bug，全部由真实数据暴露

本周修的 bug 有个一致的模式，值得记录：

| # | Bug | 为什么代码审查发现不了 |
|---|---|---|
| 1 | `git diff` 看不到未跟踪文件 → 首次运行永不提交数据 | **任务显示成功、日志无异常**，只有比对仓库状态才暴露 |
| 2 | 版本格恒显示 `—` | 上游是发布镜像，没有 release/tag；桩数据里我填了 release，正好绕过 |
| 3 | `deeptide` 被误分类为开发工具 | 因为名字里含 `ide`；我编的桩名字是 `own1/repo1`，撞不出这种巧合 |
| 4 | 中文用法被长度阈值吃掉 | 24 字符门槛按英文定，12 个汉字已是完整句子 |
| 5 | 语言切换栏被当成正文简介 | 只有真实的双语 README 才有 `English · 简体中文` 这一行 |

**共同点：我编不出我没想到的情况。** 桩数据只能验证已经想到的逻辑，验证不了现实的形状。

后半程据此调整了验证方式——不再看"任务成功了吗"，而是核对：仓库里文件在不在、线上字节与仓库是否一致、真实 payload 渲染后每一格的实际文字是什么。
